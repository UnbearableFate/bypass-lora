## What I verified (summary)

- **`read_kernel_prefix` observer.** With `observe_read=None` and `current_keys=None`, `memory` is still the original `MemoryState`. The observer only reads the query, then delegates to `state.read`. For each forward pass the step counter goes 1..S, so `run_history` records steps {1, S}. For S1 that is one record; with `fixed_query` it is two identical records. The bitwise test against 6df9e479 and the `direct == normal` real-model test cover both the prefix path and the `run_history` path.
- **Eligible sets in `prefix_read_metrics` match the state that `rb_history` actually reads:**
  - window = positions (t−w, t]: matches `M_t − M_{t−w}`.
  - strict = positions < t, with current weight 0.
  - permute = the normal key set. Keys and c are unchanged, so the address weights are identical.
  - swap = donor positions < t plus the recipient's own current token. This matches the `cat(zero, cumsum).index_select(clamp(t, L_d))` construction, so no future donor position is read, and a short donor contributes its whole sequence.
  - The normalization matches `v2_memory.read_metrics`.
  - The answer scope `labels[:,1:]!=-100` at position t aligns with the `token_losses` shift.
- **Donors.** Each donor comes from a normal `capture_history` forward of the same checkpoint, using the same candidate index, under a fixed within-task derangement. Gold labels are used only to select the gold candidate for aggregation, after both candidates have been scored. The `BranchModel` runtime is copied per layer, so all four layers are intervened together, with `use_cache=False` and the backbone attention unchanged.
- **Data.** `rb1_intervene` uses `prepare()`. `rb_data.apply_confirmation` changes only `train`, so dev is the same and no confirmation rows are touched. The candidate encoding/order guard is present.
- **iv_off = Base exactly.** For F_out, `(h+mlp(u)) + bf16(0)` is exact. For C_dual and C_up, the hook adds `0`. The check is a fail-fast exact comparison of the prediction dicts, scores included.
- **Formal-run validation** (`validate_formal_run`):
  - It rejects smoke, eval_limit, three_epochs and other-contract runs.
  - It checks config equality against the registered arm, checkpoint hash/size, and that the checkpoint path is inside the run directory.
  - It checks that the LR schedule follows `lr_factor`, and that training stopped at the first whole step at or above 2M tokens, or after three complete epochs. Both match `rb_data.plan_batches`.
  - The analysis additionally requires the nine arms to share order, split, lock, source, environment and revisions.
- **Rules 1–11** match the E-0021 Design, the H-0013..H-0016 statements and both D-0032 clarifications. All gates are inclusive Fractions. Specifically:
  - Rule 10 uses the band Base−1 ≤ arm < Base+1.
  - GC for routing is raw GC ∧ (C* defined); Rule 11 uses raw GC.
  - The S2 tie rule is a strict < 0.5. Macro scores move in 0.05 pp steps, so an exact 0.5 can occur, and it correctly goes to the higher arm.
  - C* is chosen among effective arms within strictly < 1 pp, then by parameter count, then macro, then NLL.
- **Bootstrap.** It uses `default_rng(20261101)` with 10,000 repeats. Each task's indices are drawn once per replicate and shared by every label. The intervals are the 2.5/97.5% quantiles, and each point difference is computed from the full rows.
- **Analysis modes.** Select and final both validate the nine runs, the curves at `ceil(steps·f)`, and pairing with Base on (task, id, gold, tokens). Final additionally requires:
  - exactly {01, 02, 08, 09, S_F*} intervention runs, bound by training manifest path+sha;
  - the full mode grid and the read-diagnostic strata;
  - iv_off equal to the same-allocation Base, and the T0 swap a no-op;
  - a latency grid of 01, 02, 04, 08, 07 and 07-merged on 2g, with M+c state of 16,896 bytes for 02/04/08 and 0 otherwise;
  - measured MIG usage for every training, intervention and latency attempt.
  The usage format matches `ATT-0230-1-observations.json`.
- **Latency.** The `mig_profile_guard` runs before any `make_model`. The measurement is batch 1, prefill 512 with 4 warmup and 5 timed passes, then 128 timed decode tokens after a separate warmup. The merged LoRA comes from the same RB1-07 checkpoint.
- **Base run.** ATT-0024-1 is structurally compatible: 2000 dev rows, int ids, and the expected `dev.*` metric keys. I read no accuracy values.

## Findings

### 1. Rule 8 pilot routing: progression/RB5 matrix reads as final when the pilot comes first (low)
- **Location:** `src/rb1_rules.py:275-282, 300-310, 334-341, 358-359`
- **Evidence:** Take G0 true, an effective C*, GC ≥ 1 pp, GL false, for example RB1-07 = RB1-08 = Base+2 with RB1-02 at Base. The output is:
  - `progression='draft_RB5_and_review_conclusion'`
  - `RB5_matrix=[01,05,08,03,06,07,09]` with `loop_depth=1`
  - `C_S1_S4_pilot=True`

  Rule 8 and the outcome_actions say that when GL fails and GC holds, a C-S1/C-S4 pilot runs first. If C-S4 − C-S1 ≥ 1, RB5 then runs all nine groups at a fixed S4. So the matrix and depth printed here are provisional.
- **Impact:** nonblocking. The resolved actions could be misread as releasing a 7-group S1 RB5 without the pilot.
- **Fix:**
  ```python
  pilot = bool(g0 and not gl and gc and c_star)
  if not g0: progression = 'stop_at_implementation_and_learnability_check'
  elif pilot: progression = 'C_S1_S4_pilot_then_draft_RB5_and_review_conclusion'
  elif gr or gc: progression = 'draft_RB5_and_review_conclusion'
  ...
  '7_RB5_release': {..., 'matrix_status': 'pending_C_S1_S4_pilot' if pilot else 'final',
                    'if_pilot_C_S4_minus_C_S1_ge_1pp': 'all nine RB5 groups at fixed S4 (Rule 8)' if pilot else None}
  ```
  Use the same `pilot` value in `resolved_actions`.
- **Verify:** Add a rules test for G0 ∧ GC(effective) ∧ ¬GL that asserts the new progression and `matrix_status`.

### 2. Intervention-job `normal` is never compared with, or reported against, the formal training predictions (low)
- **Location:** `src/rb1_analysis.py:224-239`; the GH reference is at `src/rb1_rules.py:227-233`.
- **Evidence:**
  - `conditions['normal']` is checked only for dev membership against Base.
  - The GH drops are measured against `RB1-02/normal`, while the GH margin against RB1-01, and every other gate, uses the training run's `predictions.json`.
  - No field records whether the two evaluations of the same checkpoint agree.

  The notes intentionally leave out a cross-job bitwise check, which is sensible because MIG slices can differ. As a result, though, a checkpoint/scorer mismatch or slice nondeterminism would not appear anywhere in the report.
- **Impact:** nonblocking.
- **Fix:** For each intervention arm, report descriptively:
  - `prediction_mismatches = Σ[normal.prediction ≠ training.prediction]`
  - `max_abs_score_difference` over both candidate scores
  - the macro difference (normal − training)
  - each job's `hardware` string

  Add these to `report['interventions_normal_vs_training']` and print them in the markdown. A hard gate is not needed.
- **Verify:** A synthetic final analysis with one flipped `normal` prediction reports mismatches = 1, and the unchanged fixture reports 0.

### 3. LR lock, source commit and Base run are bound only by internal consistency (low)
- **Location:** `src/rb1_artifacts.py:105-126`; `src/rb1_analysis.py:140-158`
- **Evidence:** Any JSON with `experiment='E-0020@1'`, `locked_lrs[family]==config.lr` and a matching split hash passes. Test fixtures build exactly such locks. The common-plan check makes the nine arms agree with one another, but it never ties that shared lock to T-0024's accepted lock. Likewise, `source.commit` is only required to be a 40-hex string common to the nine runs, and `base_run` can be any validated V1 Base. A lock that is consistent but wrong (for example a superseded or test lock), or a source commit that was not reviewed, would pass every check.
- **Impact:** nonblocking. Process controls, namely the coordinator notice and the rl run records, mitigate it.
- **Fix (self-contained):** In `validate_formal_run`, or once in `analyze`:
  1. Verify each `lock['inputs']` entry's sha256 and bytes.
  2. Require `json.loads(json.dumps(rb_train.lock_lrs([i['path'] for i in lock['inputs']]))) == lock`.

  In addition, accept `expected: {source_commit, lr_lock_sha256, base_manifest_sha256}` in the analysis input and assert it against `common` and `sources['Base']`.
- **Verify:** A test with a hand-made lock whose LR differs from the calibration outcome, but is consistent across all nine arms, is rejected. A spec whose `expected.source_commit` differs from the runs' commit is rejected.

### 4. Read-summary means count empty reads as zeros (low)
- **Location:** `src/rb_read_diagnostics.py:65-73, 96-107`
- **Evidence:** Under `iv_strict`, position 0 has `readable=0`. Its n_eff, entropy, relative_n_eff and readable values are written as 0 but still counted in `count`, and `means = sums/count`. The strict `all_valid_input` means are therefore pulled toward 0 by `empty_reads/count`, about 1/T per sequence (roughly 1% for inputs of about 100 tokens). This is not the case for the normal, window or swap conditions, which never have an empty read. `empty_reads` is reported, so the bias can be recovered, but the descriptive comparison of strict against normal n_eff and entropy is biased as printed.
- **Impact:** nonblocking (the diagnostic is descriptive).
- **Fix:** In `finish()`, also emit `nonempty_means = {name: total/(count-empty_reads) ...}` when `count > empty_reads`, and use those for n_eff, entropy, relative_n_eff and readable_positions. Alternatively, document `means` as including empty reads. `current_weight` can keep the zero convention.
- **Verify:** A `ReadSummary` test with one empty read checks that `nonempty_means['n_eff']` equals the mean over the non-empty positions.
