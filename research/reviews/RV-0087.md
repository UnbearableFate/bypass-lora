# RV-0087 answer (reviewer-2), code at a6afccb (sr/researcher-1/T-0031)

The tap, η plumbing, pairing, budget/order/LR, V1 calibration scorer, the exact tie/endpoint/non-finite selection and the gate arithmetic all match the sealed rules. ## Findings

- **Location:**
  - src/rb_tap_eval.py:176-180 (rule 1(g) raises before the calibration pass at :181-185)
  - src/rb_tap_analysis.py:164 (rule 1(a), step-0 vs the pinned Base ATT-0024-1)
  - src/rb_tap_analysis.py:169 (rule 1(g))
  - src/rb_tap_analysis.py:186-187 (rule 1(b), the pinned-Base half)
  - src/rb_tap_analysis.py:188 (`normal_same_as_final`, which is not a sealed rule-1 item)
- **Evidence:**
  - Each of these gates compares BF16 predictions produced in different PBS jobs.
  - On this system, placement on slot 3 gives a MIG 1g.24gb slice. D-0019 says that is "a large share of placements". Recorded RB runs on 1g: ATT-0217-1 (E-0020) and ATT-0240-1 (E-0021 RB1-02). The references are 2g: ATT-0247-1 (RB1-09), and ATT-0024-1, which E-0026's 2g runs matched (ATT-0300-1 checks all true).
  - D-0050 measured a 1g-vs-2g difference on RB1-02 of up to 1.86 in gold NLL, and a zero control flipped 12/1000 predictions. D-0050 adopted a same-allocation reference gate. It rejected both a cross-slice tolerance and slice control.
  - The reviewed precedents treat a normal-vs-training comparison as descriptive, with hardware as metadata: src/rb1_analysis.py:168-176 and :353, and src/rb_width_analysis.py:215. The new `normal_same_as_final` gate is stricter than both.
  - E-0028 has about 16 gated jobs. At the observed ~2/15 rate of 1g placements, P(all on 2g) ≈ 0.87^16 ≈ 0.1.
- **Impact:** resource_waste / blocked conclusion. A mismatch caused only by the slice makes rule 1 fail, so the contract says to fix the implementation and draw no conclusion.
  - In the baseline job it blocks RB1-09's calibration, and with it the η-lock.
  - In the analysis it withholds every outcome. Each training rerun costs about 0.27 node·h.
  - The measured worst case is already 5.00 of the 5.5 node·h cap (ATT-0314-1 cost-estimate.json), so two reruns exceed the cap.
- **Fix (D-0050 pattern; coordinator to confirm that this reading of rules 1(a)/(b)/(g) is acceptable, or explicitly accept the risk):**
  - **Rule 1(a):** in rb_train, for E0028 arms, read the device name after `monitor(0)`. If it is not `NVIDIA GH200 120GB MIG 2g.24gb`, score the unwrapped backbone in the same allocation and write `dev-base-same-allocation.json` with the hardware string. The analysis then gates step-0 against that file when it exists, and against the pinned Base otherwise, reporting the cross-slice comparison descriptively. On 2g this costs nothing; elsewhere it adds one dev pass of about 200 s.
    ```python
    if args.arm in E0028_ARMS and torch.cuda.get_device_name()!=PINNED_PROFILE:
        from rb1_intervene import original_backbone
        with preserved_evaluation_state(model), original_backbone(model) as backbone:
            _,base_rows=evaluate(backbone,splits,tok,args.eval_limit,split_names=('dev',))
        write_json(out/'dev-base-same-allocation.json',{'hardware':torch.cuda.get_device_name(),'predictions':base_rows})
    ```
  - **Rule 1(b):** keep `iv_off == Base_same_allocation` as the gate. Make the pinned-Base half descriptive when the intervention hardware is not 2g.
  - **Rule 1(g):** when `get_device_name() != origin['metrics']['hardware']`, also score the checkpoint on dev in the same job with the accepted E-0021 source (snapshots/7bf091d…/src, which still exists) and gate new source == old source. The comparison with the E-0021 record becomes descriptive.
    - In every case, run the calibration pass before any raise, or drop the raise and let the analysis gate, so that a mismatch does not throw away the calibration evaluation.
  - **normal_same_as_final:** make it descriptive by reusing `rb1_analysis.normal_training_agreement`.
- **Verify:**
  - Unit tests for the analysis checks:
    - pinned Base differs by a few flips, the same-allocation reference is identical, and the hardware strings differ → the checks pass and the difference is reported;
    - the same-allocation reference is perturbed → the check fails;
    - both runs are 2g and the predictions differ → the check fails.
  - Rerun the GPU smoke on the fixed commit.

## What I checked
- **Tap:** `direct_hidden` passes the input_layernorm output `n` as q, k and v (bypass_model.py:92-95, :243-244). The A dims are (1024,1024,1024) (:167). The rule 1(f) checker compares the projection's real pre-hook arguments with the norm's forward output.
- **η:** η is a Python float on LatentReader (bypass_core.py:237) and is used by the reference, prefix and T0 paths (:277, :464; read_kernel_prefix and rb_history go through `reader(...)`). It is not a parameter or a state_dict entry. On reload it comes from config.json, and `make_model` requires the reloaded config to equal `adapter_config(arm)`.
- **Configs and parameter counts:**
  - X-02 and X-03 are `kernel_tokenwise`; X-01 and the ETA arms are `memory`. All of them use C_up, r32, S1, inclusive and prefix.
  - The counts 794,624 and 925,696 match the formula.
  - The explicit `tap` leaves the E-0021 configs unchanged (ATT-0247-1 adapter config tap=qknorm_pre_rope).
  - ETA arm names and the extension grid match the contract.
- **Pairing:** `make_model` seeds after `load_base`, and creation order is the same for memory and T0. bypass_model has changed since 7bf091d only by the unused `initial_memory` argument, so the X-03 and ETA-QK initialization is RB1-09's. The registration checks and `init_digests_match_registration` cover this. ATT-0314-1's registration passed all checks.
- **Budget/order/LR:**
  - The E0028 guard enforces R1, seed 0 and LR 1e-3, plus the RBc-C=0.001 lock (verified in T-0024 lr-lock.json).
  - The split hash 34277aa… matches the file.
  - The analysis constants (13115 steps, 26230 examples, 2,000,069 input and 387,653 loss tokens, the order hash) equal ATT-0247-1.
  - The curve steps are 3279, 6558 and 9837.
  - Step-0 evaluation and the RMS pass run under `preserved_evaluation_state`, and training is deterministic.
- **Calibration:** it uses `v1_run.evaluate` on the reloaded checkpoint, in rb_train and rb_tap_eval alike. `validate_calibration` exactly reproduces evaluate's PIQA/BoolQ score, tie rule, NLL accumulation order and manifest keys. All candidates must share the same 4096 identities. Confirmation rows are taken only from train (rb_data.py:20-35), so neither calibration nor dev touches A2 or official validation.
- **Selection:**
  - Scores are exact Fractions. The tie rule is (−score, |log2(η/4⁻¹)|, η).
  - An extension is added only when all six initial points are present. η* may land on the extension, which is flagged as `grid_boundary`.
  - Only `TrainingDiverged` (non-finite loss or gradient norm, v1_run.py:206-213) on an ETA arm is excluded. OOM and evaluation failures remain partial and must rerun.
  - The lock is written with `open('x')` and records the manifest and calibration-prediction SHA256s.
  - The analysis rebuilds the lock, compares it after a JSON round trip, and binds the training manifests to the locked producers before it opens any dev file.
- **Gate arithmetic** (rules 2-4, 6, 7, 10): exact rationals; ≥ +1 pp and ≤ 0 are inclusive; rule 10 is strict `<`; d_η = 0 when η* = 0.25; the QK swap drop is 195/10000, which matches the E-0021 −1.95 (T-0025-delivery.md:146).
- **Interventions:** X-01 gets all six MODES. iv_off is checked against the same-allocation Base, iv_swap donors come from tap-agnostic rank-space history, and the read summaries use share metrics.
- **Smoke ATT-0314-1** (a6afccb, all 2g): 99 tests passed and the registration passed. The worst-case cost estimate is 4.36 to 5.00 node·h. The MIG/4 factor agrees with ATT-0247-1 (elapsed 3707 s ≈ 0.26 node·h).
