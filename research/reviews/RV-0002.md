## Findings

### 1. low (nonblocking): the cache check never compares the FP32 memory state, and the rank-128 chunk3 discrepancy is unexplained — `src/test_model.py:175-178`
Evidence: the cache check compares only BF16 logits (atol 0.50002) and write counts. In ATT-0006-1, `cache.chunk3.max_abs_err` is exactly 0.0 for every rank-32 case, even at exit std 0.5 with effects up to 6.9. At rank 128 / S=4 it is 0.171875 (inclusive) and 0.203125 (strict). The Base calibration gives exactly 0.0 for chunk3, and rank 128 also gave 0.0 at std 0.02 in ATT-0004-1. Full-prefill and chunk-3 Base features are therefore bit-identical, yet the rank-128 side branch is not reproduced bit for bit. The likeliest cause is that the FP32 GEMM rounding depends on M = B·T for the 2048→128 projection, and the difference is then amplified when it is injected in BF16. Chunking cannot change the algorithm in `process_sequence`: every timestep sees the same read rows and the same state shapes. Still, nothing records whether the difference is ulp-level, and these values sit within the tolerance only because the 2× factor absorbs them.
Fix: for chunk 3, compare `cache.memory[14].M`, `.c` (and the slots for slot backends) against `full.cache.memory[14]` at the fp32 tolerances in `tolerances.json`, and record `cache.chunk3.state.max_abs_err`. For chunk 1, record the same quantity as a diagnostic only, because the decode features legitimately differ there.
Verify: the new metric appears in the manifest. A relative error of about 1e-6 confirms numerics; anything larger points to a logic difference.

### 2. low (nonblocking): the support capacity guard applies only to slot backends — `src/bypass_model.py:155`
Evidence: under `visible_fact_delimiter`, the capacity check runs only when `backend != 'kernel_matrix'`. In the V2 factorial, a delimiter-mask construction error that writes more than 16 facts per row would therefore stop the SoftmaxSlot and KernelSlot arms but let the KernelMatrix arms train under a different n_write. Plan §16.4 pairs `slot_capacity: 16` and `slot_overflow: error` with `backend: kernel_matrix`, so the limit reads as a protocol-level write budget, not just a storage limit.
Fix: enforce `result.state.counts <= cfg.slot_capacity` for every backend whenever `phase == 'support'` and `write_scope == 'visible_fact_delimiter'`. Alternatively, record explicitly that KernelMatrix arms rely on the mask builder's own validation.
Verify: add kernel_matrix to the `slot_capacity=1` case in `test_support_delimiter_write_scope_and_capacity` and expect it to raise.
