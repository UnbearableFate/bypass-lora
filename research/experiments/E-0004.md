## Design

检查项（来源：`research/reviews/RV-0002.md` 的两条 low 跟进，`research/notes/T-0001-implementation.md` 已记录）：

| 检查 | 做法 | 通过条件 |
| --- | --- | --- |
| chunk3 记忆状态 | 同一输入分别整段前向与按 3 个 token 分块前向，比较 `cache.memory[14]` 的 M、c，slot backend 另比较 slots | FP32 atol/rtol 2e-5（`src/tolerances.json` 已锁定，不改）；记录 `cache.chunk3.state.max_abs_err` |
| chunk1 记忆状态 | 同上，逐 token 前向 | 只作诊断记录，不设通过条件（decode 特征本来就不同） |
| 写入容量保护 | `write_scope=visible_fact_delimiter` 的 support 阶段，所有 backend 执行 `counts <= slot_capacity` | kernel_matrix 加入 `slot_capacity=1` 的用例并按预期报错；slot backend 原有行为不变 |

配置：单层 index14，r128（V2 默认）与 r32；KernelMatrix、KernelSlot、SoftmaxSlot；inclusive 与 strict；S=1 与 S=4。沿用 V0 的正、负对照写法：故意让状态在分块时偏移一个元素，检查要能报错。

若 r128 的 chunk3 状态超出 FP32 容差，先确认原因（RV-0002 的推测是 2048→128 投影的 FP32 GEMM 舍入随 B·T 变化），记录在 notes 中，不放宽容差；分块或缓存记忆的实验在原因确认前暂停。
