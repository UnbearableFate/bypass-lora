### L1（low，resource_waste）：smoke、正式训练与规则 6 放行绑定同一个 source commit；成本预测不含此前的尝试
- 位置：src/rb_qvu_analysis.py:155（smoke 的 source_commit 必须等于 spec.source_commit）、:164（每条正式训练都用 spec.source_commit 校验）；
  src/rb_qvu_train.py:36（条件对照的放行要求 analysis 的 source_commit 等于当前的 SR_CODE_COMMIT）；src/rb_qvu_smoke.py:85-95（预测）。
- 证据：分析只接受与正式训练同一 commit 的 smoke（它的 registration.json 也来自那次 smoke，见 :157、:171）。
  这次审核之后只要再提交任何 commit，包括计划中的 smoke-only launcher（如果它连同正式作业一起跑在新的 commit 上），
  已经计入的 smoke 都要在新 commit 上重跑（申请 25 分钟、预期约 1000 s，约 0.07 node·h）。
  另外，`initial`/`conditional` 只加了本次 smoke 的 elapsed 和 120 s 的余量，没有加此前的尝试
  （ATT-0401-1/-2）或重跑；而契约的 2.0 上限明确“含失败”。
- 影响：浪费一次 smoke 的预算；不影响结论。
- 修复：launcher 和其他改动（如有）在计入的那次 smoke 之前一并提交，smoke、两条训练、复评、干预与分析都在同一个 snapshot 上运行；
  已经发生的用量，要么作为参数（例如 `--prior-node-hours`）加进 `initial`/`conditional`，要么在成本表里手工加总后再与上限比较。
- 验证：smoke manifest 的 metrics.source_commit、各正式 manifest 的 source.commit 与 analysis spec 的 source_commit 三者相同；
  成本表中累计用量加上预测仍 <= 1.3 / 2.0。

### L2（low，nonblocking）：规则 8 的诊断 checkpoint 一旦载入失败，会阻断规则 3/4 的分析
- 位置：src/rb_qvu_analysis.py:129-152、212、233-239；src/rb_qvu_eval.py:41、70-71。
- 证据：分析对 LEGACY 的四个 arm 都要求复评完整（`complete(...)`），同规格出现翻转、或 checkpoint 无法载入时，rb_qvu_eval 直接报错；
  RB1-01、RB1-02、RB1-09 的 calibration 还进入 `cal`/`merged`。契约规则 8 写的是：“某个 checkpoint 无法用当前代码载入时，本条只记录原因，不影响其他规则”。
  按现在的代码，只要 RB1-01/02/09 中任何一个载入失败，就算不出 d_X、d_L、d_h。实际发生的可能性低：ATT-0239-1、0240-1、0247-1 的
  adapter/config.json 与 `adapter_config(arm)`（impl=prefix）逐字段一致；uv.lock 的 sha 前缀 31429457… 与各训练 manifest 一致；
  smoke 也会用 eval-limit 16 载入这三个 checkpoint。
- 影响：只在载入失败时出现，且会按“实现检查不成立”停下，不会悄悄出错。
- 修复：允许 spec.reevaluations 对 RB1-01/02/09 写成 `{"unavailable": "<原因>"}`，这时从 cal/merged 和规则 8 中去掉该 arm，在 8_resolution 里记录原因；
  RB1-07 是规则 3 的对照，仍然必须完整。
- 验证：用缺少 RB1-02 复评的 spec 跑一次分析单测，规则 3/4 照常计算，规则 8 只记录原因。

  只报告翻转条数（契约允许）。注意 RB1-02（ATT-0240-1）本身是在 1g.24gb 上训练的。

## 已核对
- bypass_model.py:269-293：C_qvu 先计算 n = input_layernorm(h)，用 q=k=v=n 读出 z，再进入本层注意力；q_proj 的输出加 zC_q，
  对照 transformers 4.57.1 modeling_qwen3.py:200，这在 view/q_norm/RoPE 之前；v_proj 的输出加 zC_v，对照 :202，这在 view/cache/repeat_kv（GQA）之前；
  up_proj 通过 Fusion.forward 写入。注意力与 FFN 各只执行一次；hook 在 finally 里移除；lambda 用 `delta=delta` 按每次迭代绑定；
  三个出口零初始化，所以 bf16 的输出加 0 后逐位不变。旧路径只是缩进到 else 和 `if not early_read` 之下，语句没有变化。
- 参数：Qwen3-0.6B-Base 的 config（hidden 1024、16 头、8 个 kv 头、head_dim 128、intermediate 3072、无 bias）给出 r17 → 629,000、r25 → 619,400，与 PARAMETERS 一致；
  make_model 断言 stored 与 trainable，v1_train 统计 with_grad，rb_qvu_train.py:86 与 validate_formal_run 再核一次。
- 配对初始化：H 与 T0 的模块构造顺序和参数名相同，只有 A_q/A_k/A_v 在 CPU 上 randn；T0 的公式（bypass_core.py:458-465）与契约的 a_tok 定义一致；
  rb_train.adapter_config 中四个 arm 的 rank、branch、fusion、tap、eta、steps、impl 都正确。
- 训练：plan_batches 用 R1、seed0 与相同的 excluded；order sha、13,115 步、26,230 例、2,000,069 个输入 token 都写成了硬门槛；
  loss_tokens 387,653 与 ATT-0321-1、0245-1、0239-1、0240-1、0247-1 的 manifest 一致；LR lock 中 RBc-C = 1e-3；与 X-01 用同一个 v1_train。

  重载（含分数在内逐条相同）、iv_off 对 Base；8 次 dev、2 次 calibration，与预测中的计数一致。

  early-read 下 swap 同时改变 q/v/up 的写入，与 X-01 的口径一致。
- 复评：四个 ATT id 都已固定；RB1-07 的 LoRA config 与保存的一致；会报告翻转条数与 same_profile，同规格出现翻转即报错；合并分数 = 记录的 dev + 复评的 calibration。
