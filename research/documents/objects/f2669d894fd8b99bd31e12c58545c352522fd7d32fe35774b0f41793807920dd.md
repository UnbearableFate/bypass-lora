# RV-0097 answer (reviewer-2)

Candidate 61cd97b, reviewed against E-0030@1, MSG-0934 and MSG-0936. 61cd97b differs from the preflight commit 967f551 only in the seed 3/4/5 order registrations (src/seg_data.py) and notes.

Verdict: issues. One medium finding: a protocol gap in how the per-seed A2 jobs are ordered. Four low findings. The training path, the seed registration, the masking loader's equivalence, the lock and checkpoint authentication, the derangement and the rule 3-6 statistics all match the contract. I found nothing that would make a result wrong once all three A2 jobs complete.

## Findings

### 1. Medium: one seed's dev gate can fail after another seed has opened A2 (src/seg_a2_eval.py:49-61; research/notes/T-0033-run.pbs:44-48)

Each per-seed job checks only its own SEG-05 dev reproduction, then calls `read_a2` straight away. The three jobs go out as one batch and can run in any order or at the same time. The contract's remedy for a failed gate is to fix the problem, re-review, rewrite the lock and get it confirmed again, on the grounds that "A2 没有被读取，不算开封". That remedy only holds if no other seed has read A2. Rule 4 forbids a second opening. So if seed 4's gate fails after seed 3's job has written its receipt, A2 is already consumed and H-0029 can get no valid decision.

This is plausible here:
- The different-slice branch allows at most 10 flips in 2,000 rows.
- Slice assignment is not controllable. Per MSG-0934, mg1097_mig3 and mg1098_mig3 are 1g although the ledger says 2g. T-0030 had two runs land on 1g (ATT-0309-1 and ATT-0312-1).
- The cross-slice replay rate seen in this project is close to the threshold. T-0019 replayed 1,000 dev rows on 1g against 2g and got 4 mismatches, which scales to about 8 on 2,000 rows.

No test covers "gate fails, so `read_a2` is not called". test_seg_a2_eval.py:24-33 covers only a missing `--unseal` and a rejected lock.

Fix: pick one and have the coordinator accept it before the lock.
- (a) Minimal code change. In `run`, right after `validate`: if `hardware != manifests['SEG-05']['metrics']['hardware']`, write a partial manifest with `opened: false, reason: slice_mismatch` and return before the dev gate and before `read_a2`. Then resubmit on another allocation. This is stricter than rule 2(a), not looser. Any remaining gate failure is then a same-slice failure, which points to a real implementation fault. It does depart from D-0060's "不限制切片" for E-0028, so the coordinator has to accept it.
- (b) Run all three seeds' SEG-05 dev gates in one job, then open A2 for all three. This needs a contract amendment, because the contract says "每个 seed 一个".
- (c) Keep the code. Before the lock, the coordinator pre-registers that a gate failure after another seed has opened A2 counts as an engineering failure. That seed's job is then rerun unchanged under the same lock on its training slice.

Verify: add a unit test of `seg_a2_eval.run` that monkeypatches `verify_lock`, `validate`, `evaluate` and `torch.cuda.get_device_name`. With (a), a hardware mismatch, or with any design a failing gate, must leave `read_a2` uncalled, write no `a2-read.jsonl` and produce a partial manifest.

### 2. Low: nothing guarantees every A2 row can be encoded, and a failure would come after the receipt (src/seg_a2_eval.py:64-70; src/seg_data.py:39-58; src/rb_data.py:20-29)

The A2 IDs were sampled uniformly from V1 train with no encodability filter. If any A2 row raises in `encode_segments`, `evaluate` raises after the receipt. An unchanged rerun fails the same way, so A2 is used up with no result.

The risk is small:
- The E-0013 V5 runs (for example runs/ATT-0129-1, with `data.rows_per_epoch` 19443 = 13065 + 6379 − 1) audited the full V1 train before D-0025.
- Their exclusion file is the same 159-byte file b67a489d… as every later run. Its only row is piqa 5528, and an ID-only check shows 5528 is not an A2 ID.
- So all 2,000 A2 rows pass `encode_candidates`.
- What remains is the segmented-only failure: a PIQA row whose longer solution is 509 to 511 tokens, which gives `room<=0` at seg_data.py:47-49. Nothing like that has appeared in the roughly 17.4k RB-train rows or the 2,000 dev rows encoded so far.

Fix: right after `read_a2`, and before building any model, encode all 2,000 A2 rows once with `encode_segments`. If any row fails, stop with a distinct status ("A2 unencodable; no model scored"), so that no A2 score exists. Also record the E-0013 audit evidence in `preopening_checks`.

Verify: a synthetic test that puts an over-length PIQA row in the `a2` split and asserts `make_model` and `evaluate` are never called.

### 3. Low: `make_lock` forces the training source to equal the evaluation and analysis source (src/seg_a2_lock.py:18-20, 51, 67)

`make_lock` requires `inputs['training_source'] == SR_CODE_COMMIT` and validates all 12 runs against that commit. `verify_lock` then requires `evaluation_source == SR_CODE_COMMIT` for the A2 and analysis jobs. The contract allows reviewed changes to the A2 reader, evaluator and analysis after training ("之后再改这些路径，要在锁定之前重新审核"). The lock schema and `_verify_eval` already keep the two sources separate; test_seg_a2_analysis.py uses 'a'*40 for training and 'b'*40 for evaluation.

As written, any post-training change to those paths would make the 12 trained runs unlockable. The options would then be retraining (about 4.3 node·h) or an unplanned edit to `make_lock`.

Fix:
- Take `training_source` from the inputs (40 hex characters) and validate the runs against it.
- Set `evaluation_source = SR_CODE_COMMIT`.
- Keep requiring the deterministic-check producer to be at `evaluation_source`.
- Optionally record the diff between the two commits, limited to non-training paths.

Verify: a unit test of `make_lock` with synthetic run manifests at source A and the environment at commit B.

### 4. Low: the coordinator's confirmation decision is never recorded (research/notes/T-0033-run.pbs:44-48; src/seg_a2_eval.py:73-75; src/seg_a2_data.py:197-205)

The a2 stage requires `SEG_CONFIRMATION_DECISION`, but nothing passes it on, checks it or writes it to the receipt, the provenance or the manifest. Nothing in the A2 outputs shows which decision authorised the opening.

Fix: pass `--confirmation-decision D-NNNN` and check it against the pattern `D-\d{4}`. Write it to `a2-read.jsonl` and `provenance.json`. In `_verify_eval`, require it to be present and identical across the three seeds.

Verify: extend the analysis authentication test so a missing or mismatched decision is rejected.

### 5. Low: rule 7 descriptives are left out of the locked analysis (src/seg_a2_analysis.py:302-349; src/seg_a2_rules.py:212)

Rule 7 asks for PIQA, macro accuracy and NLL, the same quantities on dev, and a comparison with E-0027's dev numbers. The E-0027 locked analysis computed the PIQA and macro analogues of gain, lora and swap (`seg_seed_analysis.descriptive`).

The E-0030 analysis outputs only raw per-condition summaries. The rule-8 entry says these figures will be "supplied/reported by caller", so they would be produced after opening by code that is not locked. They do not affect rules 5 and 6.

Fix: compute the following in `analyze`:
- The per-seed and mean PIQA and macro gain, lora and swap on A2.
- The dev gain and lora from the locked final training predictions.
- The E-0027 dev reference figures, read from pinned manifests.

Verify: a synthetic test that checks the exact fractions.

## What I checked

- **Seed registration.** The seed 3/4/5 order SHA256 values in src/seg_data.py equal those in ATT-0375-1 seed-plans.json. Also checked: `SEED_ARMS`, `contract()`, the guards in `make_model` and `validate`, the unchanged init and train seed derivation, and that test_seg_seeds asserts digests that are identical within a seed and distinct across seeds.
- **Masking loader (MSG-0936).**
  - Its parse semantics match the legacy readers: PIQA line and label handling, the BoolQ `id` fallback, and the source and mapping SHA pins.
  - `apply_confirmation` regenerates the manifest and removes the placeholders before the audit.
  - In PBS it reproduces the registered seed 0/1/2 order hashes, 26,230 examples and 13,115 steps, and its exclusion audit equals ATT-0306-1.
  - I also confirmed that `plan.input_tokens` for seeds 0/1/2 (2,000,069 / 2,005,134 / 2,002,226) equals the E-0025 and E-0027 SEG-05 manifests ATT-0290-1, ATT-0307-1 and ATT-0311-1.
- **Shared code since 054a54a.**
  - The bypass_model change only adds a `normalized_qk` tap; the `qknorm_pre_rope` path is unchanged.
  - The v1_lora change refactors target paths in the same q,k,v,o,gate,up,down order and leaves the legacy `LoRALinear` CUDA init unchanged (MSG-0934).
  - rb_data, v1_data, v1_run, rb_history and seg_seed_analysis are unchanged.
- **seg_train for the new seeds.** Initial dev predictions for all four arms. For SEG-05, same-allocation Base identity at init and of iv_off after reload. Reload identity, and recording of the PBS job ID, torch/CUDA versions and hardware. `seg_artifacts.validate` enforces each of these.
- **Hardware string.** torch reports "NVIDIA GH200 120GB MIG 2g.24gb" (ATT-0375-1), so the same/different-slice comparison sees the MIG profile.
- **Lock.**
  - `make_lock`: run validation, A2/training ID disjointness via seams-train, the exclusion audit, and Keep/Reset/T0 initial-digest identity. Each hard-coded implementation check is backed by a raise earlier in the pipeline.
  - `verify_lock`: exact schema, contract and revisions; split file SHA and ids_sha256; run-root containment; hashes and sizes of the manifests, predictions and checkpoints; producer identity; derangement seed; bootstrap settings.
- **A2 job order.** `--unseal`, then `verify_lock`, then `validate`, then the SEG-05 dev gate, then the receipt, then the source read and `confirmation_manifest` regeneration, then the locked condition list.
  - SEG-00 runs through the same Base forward path as the training-time reference, and iv_off is compared with the same job's SEG-00.
  - The derangement uses `derive_seed(20261101,'residual_la_v21','A2','iv_swap')` within each task, and the analysis recomputes it.
- **Rules.**
  - Exact Fraction point estimates, strict thresholds, the fixed sequence, the +1 pp learnability threshold and the "mainly one seed" flag.
  - The bootstrap uses one index matrix shared by all arms and seeds, recomputes the max control on every draw, divides by 3·n, and uses numpy's default linear quantile.
  - It draws in chunks of 128, the same pattern as the reviewed `max_control_intervals`. As the contract specifies, it draws BoolQ indices only.
- **Analysis authentication.** Manifest, provenance, receipt count, dev-gate recomputation, row validation (tie rule and gold NLL), identical membership, gold and token counts across seeds, SEG-00 taken from seed 3, and complete cost coverage.
- **ID-only check of the A2 manifest.** SHA 34277aa4, 2×1,000 integer IDs, sealed=true, model_evaluated=false, and piqa 5528 is not among the IDs.
- **Tests.** The new tests use synthetic splits only.
- **PBS script.** Allocation check, execution from the snapshot, and stage routing.
