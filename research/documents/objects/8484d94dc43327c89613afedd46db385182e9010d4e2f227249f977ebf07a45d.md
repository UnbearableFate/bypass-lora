## Design

来源：E-0005 的 Base 结果（ATT-0043-1 / RES-0035 / EV-0032）。协调者在登录节点只读统计了 `runs/ATT-0043-1/predictions.jsonl`（不是登记的 run）：dev 上 F 线 top-1 为问题主语 944/1000、正确 13、其他支持名字 10、非名字 token 33；M 线为问题主语 767、` In` 222、正确 11。答案 NLL 从 M 线的 9.249 降到 F 线的 5.706，说明支持事实提高了正确答案的概率，但不足以改变 argmax。

数据与模型：
- 只用 calibration 切片（2,048 条，见 scope 中的路径与 sha256）。dev 已在 E-0005 评估过，这里不再评估；confirmation 不读取。
- Base 与 E-0005 相同：BF16、eager attention、完整词表，提示构造与评分沿用 `src/v2_eval.py`，不改它的行为；新增的诊断入口只 import 它。

输出（M 线与 F 线逐条）：
- 答案位置的完整词表 top-5 token 与概率；正确答案的秩（1 为最高）与概率；问题主语（`query.head`，按单 token 前导空格形式）的概率。
- top-1 类别：正确 / 问题主语 / 支持中的其他尾实体（与被问事实同关系、不同关系分开）/ 支持中的其他头实体 / 不在支持中的名字 / 非名字 token。一个名字同时是头实体和尾实体时按尾实体计。
- 限定候选准确率：在候选集合内比较同一答案位置的 logit，取最高者。(a) 支持中出现的全部不同名字；(b) (a) 去掉问题主语；(c) 与被问事实同关系的事实的不同尾实体。每个集合同时报告随机基线（按每条的 1/候选数平均）。候选名字都用单 token 前导空格形式；某个名字不是单 token 时记录并从该集合中去掉。

事实数梯度（只在 F 线上）：
- E ∈ {1,2,4,8,16}。E=16 就是原 episode。E<16 时保留被问事实，其余 E−1 条按 `derive_seed(20261029, "concat_loop_v2", "V2", "diag-fact-subset")` 派生的随机数逐条确定性抽取，保持原相对顺序，用生成器原模板重新渲染支持文本，问题不变。
- 测试要求：E=16 重新渲染后与原 `support_text` 和 `support_input_ids` 逐字一致；每个 E 变体都包含被问事实；答案 token 等于 `prompt + answer_text` 整体 tokenization 的最后一个 token。
- 每个 E 报告完整词表 EM、答案 NLL、问题主语复制率与限定候选 (a)(b)(c)。

分层（E=16 的 F 线）：被问事实在支持中的位置（`target_fact_index`，按 0–3、4–7、8–11、12–15 分四组）、关系、`support_order`、`answer_frequency_stratum`。

一致性检查：calibration 上的 M/F 完整词表 EM 与 NLL 用 E-0005 的原路径算一次，应与 dev 的量级相近；明显不同时先查原因。

判定：按 outcome_actions。结果是 diagnostic 证据，写入 V1 阶段报告与 V2 契约设计，不改 E-0005 的协议与数据。
